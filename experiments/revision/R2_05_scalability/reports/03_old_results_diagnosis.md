# 旧版低吞吐量与高运行时间诊断

数据来源仅为本次上传 `R2_05_results.zip/results_formal_merged/`。下列结果属于旧算法配置，不能用于新原始 Lifelong 基线，也不能与重建样本合并。

## 1. 结果账目与证据范围

65 条记录对应 13 条件×seeds 1001–1005：54 completed、10 timeout、1 aborted。核对每条 `runs/*.json` 与 `raw_results.csv` 中状态、seed、fleet、实际时域、完成/到达数、吞吐量和耗时，65 条均一致。

- A_base/1001 标记 aborted，保存状态停在 t=90，11 完成、54 已释放；父程序记录约 38.16 秒。该 trial 没有对应原始日志，现有材料不能确定中断的具体触发原因，不能写成算法报错或 timeout。
- A_map2_density 的五条全部 timeout，记录停在 t=120–150。
- A_map3_density 的五条全部 timeout，记录停在 t=50–60。
- 十条 timeout 的 runner 墙钟均约 1800 秒，与旧 `run.py` 的默认 `--timeout=1800` 相符。最后 checkpoint 的仿真时间不是终止时刻的精确状态，不能由 checkpoint 推断超时期间完全没有进展。
- 原目录只有 64 份日志，缺少 A_base/1001；不能称原始日志齐全。

本包保留旧 CSV、manifest、64 份原日志、65 条核对摘要；旧完整逐帧 JSON 仍在用户原始结果 ZIP 中，没有改写或覆盖。`row_reconciliation.json` 同时保留已完成试验的实现指纹和搜索计数。

## 3. 可确认的差异来源

### 3.1 输入供给与 OD 不同

原始入口在 t=0 给 3000 条积压任务，匹配函数能在最多 3×idle 数的候选中选择；旧版初始空队列，λ=.5 的 600 步运行平均只释放约 290 条。候选数量和空间分布不同，足以使任务匹配与空驶行为不同。

旧 STANDARD 工作负载还使用 p=.5 的热点混合：5 个工作站下目标概率期望为 .6/.1/.1/.1/.1；原生成器从 5 个工作站随机均匀抽取，期望为 .2/.2/.2/.2/.2。旧版同时按共同最短距离层采样 OD，不是原始的独立取货/工作站抽样。因而“地图相同、AGV 数接近”并不构成同基线。

### 3.2 实际约束与失败来源不同

旧 planner 加入无限期 current/terminal holds；尚未获得新路径的车辆会持续阻挡当前格，终点 hold 还要与未来票证比较。单通道与共享工作站条件下，这些规则可以使原先可接受的预约被拒绝。新增静态预检查和扩展上限也直接增加返回失败的来源。

| 旧条件 | segment attempts 均值 | active-hold 断连拒绝 | 扩展上限失败 | 预约拒绝 |
|---|---:|---:|---:|---:|
| 30辆，n=4 | 14124.75 | 6757.25 | 3010.00 | 1878.75 |
| 48辆，n=5 | 28943.20 | 23462.40 | 817.60 | 173.80 |

48 辆约 81.1% 的尝试因 active-hold 断连直接拒绝。这是新增规则大量参与实际运行的直接证据；不是根据源代码猜测“可能有影响”。30 辆更多尝试进入搜索并触发 5000 上限，而 48 辆更多早期拒绝，因此旧数据中 **48 辆吞吐量更低，规划总时间却小于 30 辆**，并不矛盾。

这些数据不能单独证明“某一补丁导致了全部性能下降”，因为输入、预约规则、失败处理触发频率、预热和机器环境一起变化。没有用未经控制的对比给每个原因分配因果百分比。

### 3.3 时间口径不同

Figure 9 展示 Pure Time；原入口计算 loop wall−assignment。旧 planning_seconds 是 600 步所有 batch 规划的和，旧 wall_seconds 还包括观察/验证/输出工作。因此不能用旧 wall_seconds 与论文图中的 pure time 做同口径倍数比较。执行环境也不同：旧记录为 Python 3.12.3/Anaconda/Linux，论文未提供足以重现硬件的明确资料；本次准备环境为 Python 3.12.14、NumPy 2.3.5。

特别校正：Figure 9 的 Map A、30 辆 CPS-A 红线 Pure Time 目视约为 **3 秒**，不是几十秒；几十秒更接近该面板的橙色 CMPP，或更高车队规模下的某些点。由于没有原 CSV，只能作为图读数，不能当作精确参考值。

## 4. 本轮诊断结论

地图数组不一致不受证据支持；输入供给、OD 分布、持久占用语义、搜索上限以及统计范围变化均有源码和实际记录支撑。最合适的复现起点是原始全队列输入、原匹配与原预约/失败逻辑，而不是继续在旧结果上调参追赶 Figure 9。

本轮现已完成原生seed39的500步验证：10/30/50辆吞吐量为.376/.926/1.082；恢复原始输入与算法后，单种子行为与Figure 9量级接近。30辆重复诊断保持463完成不变，但原pure时间从首次17.395秒变为后续2.049秒、1.939秒；全部观察均保留，不选择较快值冒充论文运行时间复现。正式seeds1001–1005未执行；旧补丁的因果贡献仍未做逐项消融，不能把全部时间差归于单一修改。
